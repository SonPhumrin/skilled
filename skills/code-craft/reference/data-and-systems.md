# Data and system design

The same judgment, aimed at anything that runs outside a single function call: a job, a query, a schema, a transaction. General shape here; project-specific mechanics belong in `ARCHITECTURE.md`.

**Async is infrastructure, and infrastructure defaults to no.** Do work synchronously when it finishes inside the latency budget, the caller needs the result to continue, or failure should be visible right now. Move it to a job only when it's genuinely slow, must survive the request ending, is naturally scheduled, or needs to retry independently of the caller — and say which. "It feels cleaner" isn't a reason; that's the "how much to build" question again, aimed at a queue.

**Anything that can run more than once must be idempotent.** At-least-once delivery, a retried request, a re-run migration — a second execution changing nothing isn't a nice-to-have, it's the normal operating condition of anything with retries. Prefer a mechanism where the guarantee lives with the data (a unique constraint, an upsert) over one that only checks state before acting, which two concurrent runners can both pass.

**Classify a failure before retrying it, and give retries a budget.** Transient failure (timeout, connection reset, a rate limit) deserves backoff; permanent failure (bad input, a row that no longer exists, a 404) does not — retrying it only burns the attempt budget a later transient failure might have needed. A budget matters more than it looks: three retries at every layer of a call chain three layers deep is not nine attempts on the system underneath, it's 4³ — sixty-four — because each layer's retry re-triggers all the retries below it. Cap attempts per request, and don't let more than one layer in a chain retry the same failure. Failures that exhaust their budget need to land somewhere inspectable, not a log line nobody reads; a rising failure count is a leading indicator worth watching on its own.

**A change to two places that must both happen needs one commit, not two.** Writing a record and separately notifying about it (enqueueing a job, publishing an event) are two operations that can partially fail — one commits, the other doesn't, and now the system disagrees with itself. Writing the intent to notify in the same transaction as the data change, then publishing from that written record, closes the gap; either both happen or neither does. The cost is a small delay between commit and publish, worth paying whenever a lost notification is a correctness problem, not an inconvenience.

**Measure before changing a data-access path.** Read the actual query plan or profile before touching a schema or adding an index — the answer is regularly not what the code suggests, and a speculative index costs write throughput forever for a guess. Find the slow path from data (a slow-query log, a profiler), not intuition, and optimize by total time, not the single worst call.

**A query inside a loop is the most common bug in this space (N+1).** One query fetches N rows, then the code queries once per row — invisible in review because the loop looks ordinary, invisible in development because N is three there and three thousand in production. Fetch the related data in one query up front, or batch by key, then confirm by counting queries, not by reading the code. Filter and select in the database, not after loading everything into the application.

**Pagination that walks and discards rows degrades with depth**, even when page one is instant — the failure shows up gradually, and only in production, at whatever page real usage reaches. Seeking from a stable cursor stays roughly constant regardless of depth; walking from the start doesn't. Reserve the cheap-but-degrading form for small, bounded, or admin-only sets.

**Transactions are short, and never held across a network call.** A transaction holds locks for its whole life; waiting on a third party inside one turns their latency into your lock contention and their outage into yours. Know the isolation guarantee you're actually relying on — "check if it exists, then insert" is a race under most default isolation levels; a unique constraint or an upsert closes it, hoping doesn't.

**Schema changes that touch a live table ship in stages.** Add the new shape, migrate reads and writes to it, then remove the old one — expand and contract, several small deploys instead of one that locks or rewrites a large table with no way back mid-flight.

**Connections are pooled and sized deliberately.** Opening one costs real time; an application that opens a fresh connection per unit of work spends more of it connecting than working, and more instances multiply the connection count against a server that has a hard limit — size the pool for that ceiling, not per-instance convenience.
