# Naming and function shape

The line-and-function level, where working code goes wrong in ways tests never catch, because it compiles and passes.

**Naming.** Names state intent, not type or mechanism — `activeUsers` over `userList` or `data2`; the type is already in the type. Booleans read as assertions (`isExpired`, `hasAccess`) so a reader can say the name aloud in an `if` and have it be a sentence. Functions are verb phrases named for what the caller gets, not how it happens — `findOverdueInvoices` beats `queryInvoiceTableWithDateFilter`, which lies the moment you add a cache. Length scales with the distance between declaration and use, not lifetime alone (Ousterhout): a loop index declared and used two lines apart can be `i`; a name a reader must carry across a file, or that lives for years as an export, needs enough clues to stand alone without the reader holding the definition in their head. One concept, one word, everywhere — if it's `Reconciliation` in the schema, it isn't `Settlement` in the service; when `CONTEXT.md` exists, use its terms exactly. Reveal the unit — `timeoutMs`, `priceCents` — units in names have prevented more bugs than any comment. A name you cannot find is a design signal: the function is doing more than one thing.

**Function shape.** One level of abstraction per function — a function that both orchestrates and manipulates bytes forces the reader to change altitude mid-read. Guard clauses over nesting: handle the exceptional and early-exit cases first, then let the happy path run flat. Nesting past three levels is the refactor signal — extract the inner block, invert a condition into a guard, or move the loop body out. Past roughly ten independent branches (each `if`, `&&`, `case`, `catch`, loop counts one), the function has become several functions sharing an indentation level. No boolean flag parameters — `render(data, true)` tells the reader nothing; write `renderCompact` and `renderFull`. Parameter count is a design signal: past three or four, the ones that always travel together want to be one type.

**Control flow.** Return early rather than nesting toward one return at the bottom. Extract complex conditions into named predicates — `isEligibleForRefund(order)` documents the rule where a reader will look. Pick loop form for clarity, not doctrine: `map`/`filter`/`reduce` say what the result is; a plain loop is clearer when the body has side effects or needs an early exit. Name the loop's product (`const overdue = ...`) rather than accumulating into `result`. Don't mutate a parameter the caller still holds. Handle the whole space — exhaustive `switch` with no silent default, so a new case breaks the compile rather than falling through in production.

**Comments.** Comment the why, never the what — a comment restating the code is a naming bug with extra steps, and it goes stale the first time the code changes. Write one when the reader would otherwise ask a question the code can't answer: why this looks wrong but is correct, an invisible ordering constraint, a workaround with the upstream issue linked, why a slower approach was chosen, the spec a magic number comes from. Delete commented-out code — version control already has it. A `TODO` carries a name and a condition, or it's decoration.

**Errors at the line level.** Never swallow — a bare `catch {}` converts a fault into a mystery. Errors carry context: "failed to load invoice 4821 for tenant acme: connection timeout" beats "failed to load." The failure path is as readable as the success path; it's the one that runs when someone's already having a bad day. Catch narrow — catching the base error type to handle one case buries the four you didn't anticipate.
